
# HTTP

- **HyperTex Transfer Protocol** (HTTP) là giao thức tầng ứng dụng của Web -> Được triển khai trong 2 chương trình: một chương trình client và một chương trình server, chúng giao tiếp với nhau bằng cách trao đổi thông điệp HTTP, HTTP định nghĩa format của chúng
	1. **Client**: trình duyệt (browser) yêu cầu, nhận (sử dụng giao thức HTTP), và "hiển thị" các đối tượng Web
	2. **Server**: Máy chủ (web server) gửi (sử dụng giao thức HTTP) các đối tượng đáp ứng cho yêu cầu
![[Pasted image 20250911105214.png]]

- Một số thuật ngữ:
	- **Trang web** bao gồm một số **đối tượng** (object)
	- Đối tượng có thể là tệp HTML, ảnh JPEG, Java applet, tệp audio,...
	- Trang web bao gồm **tệp HTML cơ bản** chứa **một số đối tượng được tham chiếu**
	- Mỗi đối tượng được định địa chỉ bởi một **URL**: `www.name.edu/someDepartment/pic.png` -> `www.name.edu` là tên host, `/someDepartment/pic.png` là tên đường dẫn 

- Khái quát về HTTP:
	- **Dùng TCP**:
		- Client khởi tạo kết nối TCP (tạo socket) tới server, cổng 80
		- Server chấp nhận kết nối TCP từ client
		- Thông điệp HTTP (giao thức tầng ứng dụng) được trao đổi giữa trình duyệt (HTTP client) và máy chủ Web (HTTP server)
		- Đóng kết nối TCP
	- **HTTP là "không trạng thái"** (Stateless):
		- Server không lưu giữ thông tin về những yêu cầu trước đó của client 

- Giao thức lưu giữ “trạng thái” khá phức tạp!
	- Lịch sử quá khứ (trạng thái) cần phải được lưu giữ
	- Nếu server/client bị sự cố, thì quan điểm về “trạng thái” của chúng có thể không nhất quán, cần phải được hòa giải

## HTTP không bền vững, HTTP bền vững

### HTTP không bền vững

- HTTP không bền vững:
	- Chỉ có tối đa một đối tượng được gửi qua một kết nối TCP -> Kết nối sau đó sẽ đóng lại
	- Việc tải về nhiều đối tượng sẽ yêu cầu nhiều kết nối

- Giả sử trang web có HTML cơ bản và 10 ảnh JPEG, 11 đối tượng trên ở cùng 1 server, URL là `http://www.someSchool.edu/someDepartment/home.index` 
	1. HTTP client tại kết nối TCP đến server `http://www.someSchool.edu` ở cổng 80 (cổng mặc định cho TCP)
	2. HTTP client gửi yêu cầu HTTP đến server qua socket. Yêu cầu gồm tên đường dẫn `/someDepartment/home.index`
	3. HTTP server nhận và xử lí yêu cầu qua socket -> Lấy đối tượng `/someDepartment/home.index` ở bộ nhớ (RAM hoặc ổ nhớ) -> đóng gói đối tượng vào một thông điệp phản hồi HTTP -> Gửi lại cho client qua socket
	4. HTTP server bảo TCP đóng kết nối (TCP đóng khi nào đảm bảo client đã nhận được thông điệp)
	5. HTTP client nhận thông điệp -> TCP đóng kết nối -> Thông điệp nhận được là đối tượng HTML -> Giải nén -> Tìm tham chiếu đến 10 ảnh JPEG
	6. Lặp lại 4 bước đầu cho mỗi ảnh được tham chiếu
=> Tổng cộng 11 kết nối TCP được tạo (10 lần kết nối TCP tham chiếu ảnh có thể được gọi song song)

- Để tính toán ước lượng thời gian trôi qua từ khi client yêu cầu đến khi nhận được toàn bộ -> **round-trip time** (RTT) 
- RTT là thời gian để cho một gói tin nhỏ đi từ client -> server -> client 
- RTT bao gồm: độ trễ lan truyền gói tin, độ trễ xếp hàng gói tin tại các router và switch trung gian, và độ trễ xử lý gói tin

- Thời gian đáp ứng HTTP (khi client ấn vào 1 hyperlink)
	- Một RTT để khởi tạo kết nối TCP
	- Một RTT để gửi yêu cầu HTTP và một vài byte HTTP phản hồi được trả về
	- Thời gian truyền tệp (server lấy ảnh, video,... từ bộ nhớ và truyền đến client qua mạng)

=> Thời gian đáp ứng của HTTP không bền vững = 2 * RTT + thời gian truyền tệp

### HTTP bền vững

- HTTP bền vững:
	- Nhiều đối tượng có thể được gửi qua một kết nối TCP duy nhất giữa client và server

- Server sẽ để kết nối TCP mở sau khi gửi phản hồi 
- Chuỗi các thông điệp HTTP tiếp theo sẽ được gửi thông qua kết nối mở này
- Client gửi yêu cầu ngay sau khi gặp một đối tượng được tham chiếu
- Ít nhất là 1 RTT cho tất cả các đối tượng được tham chiếu 

## Định dạng thông điệp HTTP

- Có 2 kiểu thông điệp HTTP: request message (thông điệp yêu cầu) và response message (thông điệp đáp ứng)

### Thông điệp yêu cầu

- Thông điệp yêu cầu thường có dạng như sau (có thể có nhiều hơn hoặc có thể chỉ có 1 dòng)
```
GET /somedir/page.html HTTP/1.1 \r\n
Host: www.someschool.edu \r\n
Connection: close \r\n
User-agent: Mozilla/5.0 \r\n
Accept-language: fr \r\n
```

- Dòng đầu tiên là **request line**, gồm
	- **method field**: `GET` (có thể là `POST`, `HEAD`, `PUT`, `DELETE`)
	- **URL field**: `/somedir/page.html`
	- **HTPP version field**: HTTP 1.1 
- Các dòng tiếp theo là **header lines**, cung cấp thông tin client gửi đến server (Host, Connection, User-agent, Acccept-language)
- `\r` là carriage return (trở về đầu dòng), `\n` là line feed (xuống dòng)
![[Pasted image 20250911133615.png]]

- Phần "entity body" sẽ trống khi dùng `GET`, nó sẽ được dùng cùng với `POST` e.g. khi người dùng điền một form, có thể là từ khóa cho công cụ tìm kiếm -> Nếu là `POST`, phần thân bao gồm input của người dùng từ form đó 

- Tuy nhiên, HTML form sẽ không dùng `POST`, nó dùng `GET` và cho các từ khóa (ở form) vào URL được yêu cầu e.g. `monkeys`, `bananas` -> `www.somesite.com/animalsearch?monkeys&bananas`

- `HEAD` khá giống với `GET` -> Trả về thông điệp HTTP nhưng chừa lại đối tượng được yêu cầu -> Thường dùng cho debugging

- `PUT` thường được dùng cùng với công cụ xuất bản Web (Web publishing tool) -> Cho phép người dùng tải đối tượng lên một đường dẫn (thư mục) xác định trên một Web server cụ thể

- `DELETE` cho phép người dùng, hoặc ứng dụng xóa một đối tượng trên Web server

### Thông điệp đáp ứng 

- Có dạng như sau
```
HTTP/1.1 200 OK
Connection: close
Date: Tue, 09 Aug 2011 15:44:04 GMT
Server: Apache/2.2.3 (CentOS)
Last-Modified: Tue, 09 Aug 2011 15:11:03 GMT
Content-Length: 6821
Content-Type: text/html
(data data data data data ...)
```

- Gồm 3 phần: **status line**, 6 **header lines** và **entity body**
- Phần status line sẽ gồm 3 miền: protocol version, status code, và status message
- Phần header line sẽ cho ta biết thêm các thông tin cụ thể liên quan đến thông điệp đáp ứng
- Phần entity sẽ bao gồm những đối tượng được yêu cầu 
![[Pasted image 20250911135638.png]]

- Status code xuất hiện ngay trong dòng đầu tiên của thông điệp đáp ứng từ server đến client
	- `200 OK`-> Yêu cầu thành công, đối tượng yêu cầu nằm sau thông điệp này
	- `301 Moved Permanently` -> Đối tượng yêu cầu bị di chuyển, vị trí mới được xác định ở phía sau thông điệp này (`Location:...`)
	- `400 Bad Request` -> Server không tìm thấy thông điệp yêu cầu
	- `404 Not Found` -> Tài liệu yêu cầu không có trong server này 
	- `505 HTTP Version Not Supported` -> Phiên bản HTTP không được hỗ trợ bởi server

# Cookies

- HTTP server là stateless -> Giúp đơn giản hóa thiết kế server, giúp phát triển được các Web server có thể chạy được hàng nghìn kết nối TCP cùng lúc 
- Để lưu và nhận dạng người dùng, HTTP sử dụng cookies. Cookies cho phép các trang web lưu người dùng 

- Cookies gồm 4 phần:
	1. Cookie header line ở thông điệp HTTP đáp ứng
	2. Cookie header line ở thông điệp HTTP yêu cầu
	3. Cookie file được lưu ở máy người dùng
	4. Back-end database của trang web

- Ví dụ:
	- Susan thường truy nhập Internet từ một PC
	- Cô ấy vào một trang thương mại điện tử lần đầu tiên
	- Khi yêu cầu HTTP khởi tạo đi đến trang, trang sẽ tạo ra:
		- Một ID duy nhất
		- Điểm truy nhập vào cơ sở dữ liệu back-end cho ID
	- Khi lần tiếp theo đến trang web đó, client sẽ gửi yêu cầu HTTP với ID cookie riêng -> Giúp dữ trạng thái người dùng

# Web caching

### Khái niệm

- **Web cache**, hay **proxy server** là thực thể mạng mà thỏa mãn yêu cầu HTTP thay mặt cho Web server gốc 
- Web cache có bộ nhớ riêng và giữ các bản sao chép của các đối tượng được yêu cầu gần đây

- Trình duyệt của người dùng có thể được thiết lập để tất cả yêu cầu HTTP được gửi đến Web cache -> Giả sử đã thiết lập và trình duyệt yêu cầu đối tượng tại `http://www.someschool.edu/campus.gif`
	1. Trình duyệt khởi tại kết nối TCP đến Web cache và gửi yêu cầu HTTP
	2. Web cache kiểm tra xem nếu nó có đối tượng yêu cầu lưu sẵn -> nếu có thì trả đối tượng về trong thông điệp đáp ứng HTTP 
	3. Nếu không có -> Mở kết nối TCP đến máy chủ gốc (`www.someschool.edu`) -> Gửi yêu cầu HTTP với đối tượng vào kết nối TCP cache-to-server -> Sau khi nhận được, máy chủ gốc gửi đối tượng được yêu cầu đến Web cache qua đáp ứng HTTP
	4. Khi nhận được -> Web cache tạo bản sao chép và lưu tại bộ nhớ và gửi đối tượng đó đến client qua thông điệp đáp ứng HTTP (thông qua kết nối TCP trước đó)

- Cache vừa là server vừa là client tùy vào ngữ cảnh nhận/gửi thông điệp

### Get có điều kiện

- Dù caching có thể giúp giảm thời gian phản hổi -> Gây ra một vấn đề mới - nếu bản sao chép đối tượng đó trong cache đã bị thay đổi ở server gốc 
- HTTP có cơ chế để giúp cache xác minh lại nếu đối tượng đó đã được cập nhật hay chưa -> **conditional GET**
- Một thông điệp yêu cầu HTTP là thông GET có điều kiện nếu
	1. Thông điệp yêu cầu sử dụng `GET`
	2. Thông điệp yêu cầu có chứa header line `If-Modified-Since: `

- Minh họa hoạt động
1. Thay mặt cho trình duyệt yêu cầu, proxy cache gửi thông điệp yêu cầu đến Web server
```
GET /fruit/kiwi.gif HTTP/1.1
Host: www.exotiquecuisine.com
```
2. Web server gửi thông điệp đáp ứng với đối tượng được yêu cầu
```
HTTP/1.1 200 OK
Date: Sat, 8 Oct 2011 15:39:29
Server: Apache/1.3.0 (Unix)
Last-Modified: Wed, 7 Sep 2011 09:23:24
Content-Type: image/gif
(data data data data data ...)
```
-> Cache chuyển tiếp đối tượng về trình duyệt yêu cầu và lưu bản sao tại bộ nhớ (lưu `last-modified date` cùng với đối tượng)
3. 1 tuần sau, một trình duyệt khác yêu cầu đối tượng này, và nó vẫn ở trong cache. Do đối tượng có thể đã bị thay đổi -> thực hiện kiểm tra cập nhật qua `GET` có điều kiện
```
GET /fruit/kiwi.gif HTTP/1.1
Host: www.exotiquecuisine.com
If-modified-since: Wed, 7 Sep 2011 09:23:24
```
-> `If-modified-since = Last-Modified`. Giả sử đối tượng chưa bị thay đổi 
4. Server gửi lại đáp ứng
```
HTTP/1.1 304 Not Modified
Date: Sat, 15 Oct 2011 15:39:29
Server: Apache/1.3.0 (Unix)
(empty entity body)
```
-> Có thể thấy web server vẫn gửi phản hồi nhưng mà **không có** đối tượng được yêu cầu -> Tiết kiệm băng thông
